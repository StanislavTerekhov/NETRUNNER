# Фаза 2 — LOCAL INTELLIGENCE + FORGE: отчёт

Дата: 2026-10-30. Статус: **завершена**. Версия 0.2.0.

## Модели

| Модель | Роль | Размер | Измерено на этой машине |
|---|---|---|---|
| `qwen3.6:35b` (35B MoE, 3B активных, 256K ctx, tools/thinking/vision) | Основная модель NETRUNNER, учитель и судья для FORGE | 22 ГБ Q4_K_M | 57% CPU / 43% GPU (9 ГБ VRAM), 13–32 ток/с, холодная загрузка 14–58 с |
| `qwen3:8b` | База для дообучения и эталон сравнения | 5,2 ГБ | полностью в VRAM, ~55 ток/с |
| `netrunner-qwen3:8b` | **Дообученная локально модель** (QLoRA на коде NETRUNNER) | 4,7 ГБ Q4_K_M | полностью в VRAM, 58–70 ток/с |

Почему не более крупные Qwen: `qwen3-coder-next` (52 ГБ) почти полностью занимает RAM; `qwen3.5:122b` (81 ГБ) и `qwen3-coder:480b` (290 ГБ)
не помещаются в 64 ГБ RAM + 12 ГБ VRAM.

## Что сделано в приложении

- **Ollama-бэкенд** в main-процессе: статус, список, детали (`/api/show`: capabilities, контекст, архитектура), запущенные модели
  с реальным разделением VRAM/RAM (`/api/ps`), загрузка/выгрузка, удаление (нативный диалог подтверждения в main), загрузка моделей
  с прогрессом, потоковый чат с отменой и реальными метриками (ток/с, токены промпта, время загрузки).
- **Model Vault**: карточки моделей, оценка размещения (VRAM / гибрид / не помещается) + фактическое измерение после загрузки,
  модель по умолчанию, железо (CPU/RAM из ОС, GPU/VRAM из `nvidia-smi` — WMI занижает VRAM до 4 ГБ), сетевой режим,
  загрузка моделей, панель **FORGE** с отчётами обучения.
- **Neural Core**: сессии (сохраняются в `userData/conversations/*.json`, в Фазе 4 → SQLite), выбор модели, размер контекста,
  режим рассуждений (только если модель его поддерживает), системный промпт, прикрепление открытого в редакторе файла,
  остановка генерации, рендер кода без HTML-инъекций.
- **Сетевые режимы** STRICT OFFLINE / LOCAL NETWORK / ONLINE TOOLS — проверяются в main-процессе при каждом запросе:
  эндпоинт инференса только loopback (LAN — вне strict offline), публичные хосты запрещены в любом режиме,
  загрузка моделей только в ONLINE TOOLS.
- **Блокировка облачных моделей Ollama** (`*:cloud`, `*-cloud`, `remote_host`): Ollama умеет проксировать модели, работающие
  на ollama.com. Такие модели скрыты и отклоняются в чате/загрузке/pull — и в приложении, и в скриптах FORGE.
- Фильтр утечки тегов `<think>`/`</think>` в начале потока ответа (см. «Найденные дефекты»).

## FORGE — обучение весов

Конвейер `forge/` (подробно: [forge/README.md](../forge/README.md)), всё локально:

1. `build_dataset.py` — `qwen3.6:35b` прочитала 79 фрагментов кода NETRUNNER и сгенерировала вопросы/ответы, привязанные к коду
   (18 мин, 38 192 токена, 0 сбоев) + примеры идентичности/политики. Итог: **298 train / 36 eval**.
2. `train_qlora.py` — QLoRA (Unsloth, r=32, все проекции, 3 эпохи, loss только по ответам) на `unsloth/Qwen3-8B-unsloth-bnb-4bit`,
   выполнено с `HF_HUB_OFFLINE=1`. **7,6 мин, пик 8,3 ГБ VRAM**.
3. `merge_lora.py` — слияние адаптера с bf16-весами на CPU, офлайн (65 с).
4. `export_ollama.py` — `convert_hf_to_gguf.py` → `llama-quantize` Q4_K_M → `ollama create netrunner-qwen3:8b`
   (шаблон чата скопирован из официального `qwen3:8b`).
5. `evaluate.py` — обе модели отвечают на 36 отложенных вопросов, `qwen3.6:35b` оценивает 0–10 против эталона.

### Результаты (реальные)

| Метрика на 36 отложенных вопросах | qwen3:8b (база) | netrunner-qwen3:8b |
|---|---|---|
| eval loss (перплексия) | 3,070 (21,5) | **1,542 (4,67)** |
| Оценка судьи, среднее 0–10 | 3,14 | **3,72** |
| Token-F1 с эталоном | 0,20 | **0,38** |
| Победы / ничьи / поражения | — | 15 / 12 / 9 |

**Интерпретация, без приукрашивания.** Знания о проекте перешли в веса: перплексия на отложенных вопросах упала в 4,6 раза,
модель чаще называет правильные файлы и механизмы, а база на тех же вопросах уверенно выдумывает API. Но абсолютное качество
фактов низкое (3,7/10): 298 примеров мало, и на общих вопросах дообученная модель местами стала хуже
(«зачем `noEmit` в tsconfig» — 9 → 2). Для точных фактов о коде правильный инструмент — поиск по коду (RAG, Фаза 4);
дообучение лучше подходит для стиля, соглашений проекта и поведения.

Что улучшит v2: больше данных (перефразирования, 8–10 пар на фрагмент), смешивание с общими данными для защиты от забывания,
примеры с рассуждениями (см. ниже), 2 эпохи вместо 3, оценка на вопросах по коду, полностью исключённому из обучения.

## Найденные и исправленные дефекты

1. **Виртуализация AppData.** Claude Desktop — MSIX-приложение; файлы, записанные из его дочерних процессов в `%LOCALAPPDATA%`,
   попадали в `Packages\Claude_…\LocalCache` и были невидимы снаружи. FORGE перенесён в `%USERPROFILE%\NETRUNNER\forge`.
2. **Конфликт зависимостей.** `requirements-convert_legacy_llama.txt` llama.cpp пинит `transformers==4.57.6` и откатил версию,
   нужную Unsloth. Конвертер вынесен в отдельный `convert-venv`.
3. **Unsloth `save_pretrained_merged` требует интернет** (проверяет модель на Hub даже при наличии кэша) — заменён
   собственным `merge_lora.py` на transformers+peft.
4. **Ollama 0.40 не квантует GGUF при `create`**, а для safetensors поддерживает только int4/int8/nvfp4/mxfp4/mxfp8 —
   квантование выполняется официальным `llama-quantize` (релиз llama.cpp b12018, CPU-сборка).
5. **Дообученная модель потеряла режим рассуждений.** Обучающие ответы были без рассуждений, поэтому модель научилась
   всегда пропускать `<think>`, а в THINK-режиме в ~1 из 3 ответов выдавала `</think>` текстом. Исправлено: фильтр в
   клиенте (защищает от любой Qwen-модели), THINK по умолчанию выключен; для v2 нужны примеры с рассуждениями.
6. Панель HARDWARE растягивалась на всю высоту и выталкивала остальные (Tailwind `h-full` vs `h-auto`) — у `Panel` появился режим `fit`.
7. PowerShell 5.1 `Get-Content`/`Set-Content` испортил UTF-8 (— и …) в двух файлах — исправлено, BOM удалены.

## Ограничения и блокеры

- **llama.cpp и LM Studio как бэкенды приложения** не реализованы (вы выбрали Ollama); интерфейс клиента рантайма готов
  к добавлению адаптеров OpenAI-совместимого API.
- Ollama-приложение само проверяет обновления — это вне контроля NETRUNNER. Для строгого офлайна отключите автообновление
  в настройках Ollama или правилом брандмауэра (Фаза 5).
- `qwen3.6:35b` на этой машине — 13–32 ток/с из-за выгрузки экспертов на CPU; для интерактивного кодинга быстрее
  `netrunner-qwen3:8b`/`qwen3:8b` (55–70 ток/с).
- Бинарники `llama-quantize` из релиза llama.cpp не подписаны (официальный GitHub-релиз ggml-org).
- Сессии чата пока JSON-файлы; перенос в SQLite — Фаза 4.
