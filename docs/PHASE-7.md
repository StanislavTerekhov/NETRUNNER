# Фаза 7 — переход на llama.cpp и модели Qwen3-Coder-Next / Qwen3.8-27B

Дата: 2026-10-31. Версия 1.1.0. Решения пользователя: Ollama удалить полностью; основная общая модель — Qwen3.8-27B,
кодовая (агенты) — Qwen3-Coder-Next; дообучение — на самой новой малой Qwen (большие модели на 12 ГБ VRAM не обучаются).

## Рантайм

NETRUNNER больше не зависит от Ollama. Инференс — официальная CUDA-сборка llama.cpp (`llama-server`, b12020),
которой управляет сам NETRUNNER:

- **Каталог моделей** — GGUF-файлы в `%USERPROFILE%\NETRUNNER\models`. Метаданные читаются из заголовка GGUF (архитектура,
  контекст, MoE, шаблон чата → tools/thinking; `pooling_type` → эмбеддинги). Разбитые на части файлы — одна модель;
  незавершённые загрузки не показываются; `mmproj` прикрепляется к своей модели (изображения/видео для Qwen3.8-27B).
- **Процессы** — `llama-server` на свободном loopback-порту, со случайным API-ключом на каждый запуск, без web UI.
  Слот чата (чат и агенты) и слот эмбеддингов. Обе большие модели одновременно в 64 ГБ RAM не помещаются — слот чата
  переключает модель; пока работает движок агентов, его модель закреплена.
- **Размещение** — `--fit on`: llama.cpp сам раскладывает слои и MoE-экспертов между GPU и CPU под свободную VRAM.
  `-b/-ub 4096` для MoE, 2048 для плотных (см. замеры).
- **Роли моделей** — GENERAL (чат), AGENT (инструменты), MEMORY (эмбеддинги); назначаются в MODEL VAULT, иначе выбираются
  автоматически.
- **Загрузки** — из Hugging Face в формате `owner/repo:QUANT` (только ONLINE TOOLS, с докачкой, каждая запись — в журнале
  сети). **Установка рантайма** — кнопкой SETUP из официального релиза ggml-org/llama.cpp на GitHub (CUDA + cudart
  при наличии NVIDIA, иначе CPU-сборка).
- VRAM модели — разница занятой памяти GPU до и после загрузки (Windows WDDM не отдаёт VRAM по процессу).

## Замеры на этой машине (RTX 3060 12 ГБ, 64 ГБ RAM, llama.cpp b12020)

| Модель | Загрузка | Генерация | Обработка промпта |
|---|---|---|---|
| Qwen3-Coder-Next Q4_K_M (MoE 80B/3B) | 27–101 с (холодный диск) | 4,2 ток/с первый ответ → **15,8–19,9 ток/с** прогретая | 12,5K токенов: 50→120 ток/с; **с `-ub 4096`: 106→328 ток/с** |
| Qwen3.8-27B UD-Q4_K_M (плотная) | ~10 с | **2,9 ток/с** | 19–29 ток/с (короткий промпт) |
| Qwen3.8-27B UD-IQ3_XXS | ~20 с | **6,3 ток/с** | 5–7 ток/с (короткий промпт) |
| Qwen3-Embedding-0.6B Q8_0 | 2 с | индексация репозитория: **17 с** (было 92 с на Ollama) | поиск 15–26 мс |

Вывод: плотная 27B на 12 ГБ VRAM упирается в чтение части весов из RAM на каждом токене — быстрее 3–6 ток/с она здесь не будет.
По умолчанию GENERAL = IQ3_XXS (вдвое быстрее), Q4_K_M — качественнее, назначается звёздочкой. Coder-Next (MoE) быстрее
27B, потому что на токен активны 3B параметров; первый ответ после загрузки медленный — модель (48 ГБ) подкачивается с диска.

## FORGE v2 — дообучение весов

Большие модели (27B плотная, 80B MoE) на 12 ГБ VRAM не обучаются даже в 4 бита, поэтому схема — «учитель/ученик»:
Qwen3-Coder-Next генерирует вопросы-ответы по коду проекта, ученик **Qwen3.5-4B** (самая новая малая Qwen, помещается
в bf16 LoRA) учит их в весах, Qwen3.8-27B судит результат. Всё локально, без сети (`HF_HUB_OFFLINE=1`).

| Этап | Результат |
|---|---|
| Датасет | 186 фрагментов → **675 train / 84 eval**, 0 сбоев; учитель 185 вызовов, 5631 с |
| Обучение | bf16 LoRA r=16, 3 эпохи, 13 мин, пик VRAM 8,9 ГБ; train loss 1,94 → ~0,7 (среднее 1,07); **eval loss 1,968 → 1,555 (перплексия 7,16 → 4,74)** |
| Экспорт | `models/netrunner/netrunner-qwen3.5-4b-Q4_K_M.gguf` 2,5 ГБ (и база `qwen3.5-4b-base-Q4_K_M.gguf` для сравнения) |
| Оценка (84 отложенных вопроса, судья Qwen3.8-27B IQ3_XXS) | балл судьи **1,36 → 2,20** из 10; F1 по токенам **0,19 → 0,40**; дообученная лучше в 36, хуже в 12, равны в 36 |

Как читать: тест «закрытой книги» — модель отвечает по памяти, без доступа к файлам. База обычно отвечает «не вижу
ваш файл» и придумывает типичную реализацию; дообученная знает имена и устройство проекта, но 4B-модель запоминает
детали неточно, поэтому абсолютные баллы низкие. Для работы с кодом агенты используют Coder-Next с реальным доступом
к файлам и памятью проекта; дообученная 4B — быстрый «знаток проекта» для чата (назначается звёздочкой в MODEL VAULT).

## Найденные и исправленные дефекты

1. Шаблон загрузки Coder-Next не совпал со структурой репозитория (папка `Qwen3-Coder-Next-Q4_K_M/`, а не `Q4_K_M/`) — исправлено.
2. Выбор файлов из репозитория HF: запрос `Q4_K_M` захватывал и `UD-Q4_K_M`; `F16` совпадал с `BF16` — исправлено, покрыто тестами.
3. `nvidia-smi` в Windows не показывает VRAM по процессу (`[N/A]`) — используется разница до/после загрузки.
4. Агент Coder-Next сначала пишет команды с `&&`, которые не работают в Windows PowerShell 5.1, — сам повторяет с `;`
   (лишний шаг, не ошибка NETRUNNER).
5. Генерация датасета захватывала `unsloth_compiled_cache/` (592 фрагмента вместо 186) — каталог исключён.
6. Деинсталлятор Ollama завершает **все** процессы `llama-server.exe` (совпадение имени) — учитель FORGE погиб на 2-м фрагменте,
   и скрипт пометил бы остальные как сбойные. Теперь `LlamaServer.chat` останавливает прогон, если сервер умер.
7. **`merge_lora.py` молча не применял адаптер**: Qwen3.5 — VL-модель, адаптер обучен на ключах `model.language_model.*`, а слияние
   загружало текстовый класс с ключами `model.layers.*` — peft выдал лишь предупреждение, и «дообученный» GGUF был копией базы.
   Исправлено (загружается тот же класс), и добавлена проверка: если веса после слияния не изменились — ошибка.

## Ограничения

- Qwen3.8-27B на 12 ГБ VRAM — 3–6 ток/с; Coder-Next — до ~20 ток/с, но 48 ГБ и долгий первый ответ.
- LM Studio как источник моделей не подключён (llama.cpp читает те же GGUF — файлы LM Studio можно положить в папку models).
- ripgrep не поставляется (решение пользователя), установщик и бинарники llama.cpp не подписаны.
