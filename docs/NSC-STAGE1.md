# NSC, этап 1 — переиспользование разобранного контекста между шагами агентов

Дата: 2026-11-04. Модель агентов: Qwen3-Coder-Next Q4_K_M, llama.cpp b12020. Данные — `%USERPROFILE%\NETRUNNER\nsc\stage1\`.

## Почему каждый новый шаг читал промпт заново

Этап 0 показал: внутри шага кэш llama.cpp работает (96–99 % промпта не пересчитывается), а каждый новый шаг конвейера (ARCHITECT → CODER → DEBUGGER → REVIEWER) читает свой промпт целиком, 7–7.5 тыс. токенов, ~28 с на шаг.

Что OpenCode на самом деле отправляет модели — снято подставным сервером без модели (`test/nsc/stage1-capture.live.test.ts`):
- Системный текст ~1.3 тыс. символов начинался с роли: «You are ARCHITECT…», «You are CODER…».
- Описания инструментов — 11–20 тыс. символов, и набор у ролей был разный: у ARCHITECT нет `bash`/`edit`/`write`, у REVIEWER и OPERATOR нет `edit`/`write`. OpenCode убирает запрещённые инструменты из списка.
- Общая часть промптов разных ролей — **8 символов** («You are »). Переиспользовать было нечего.

## Как llama.cpp переиспользует префикс у Coder-Next

Coder-Next — гибридная модель: в ней есть рекуррентные слои, а их состояние нельзя «отмотать» на произвольный токен. Отмотать можно только до сохранённой контрольной точки. Замеры (`test/nsc/stage1-prefix.live.test.ts`, `stage1-prime.live.test.ts`):

| Где расходятся промпты | Переиспользовано |
|---|---|
| Только в последнем сообщении пользователя | всё до этого сообщения (5025 из 5041; 5313 из 6912 на реальных промптах агентов) |
| Внутри системного текста, ~4 тыс. токенов до конца | только до точки «за одну порцию до конца»: 945 токенов при `-ub 4096`, 3040 при 2048, 4050 при 1024 |

- Уменьшать порцию (`-ub`) невыгодно: холодное чтение промпта падает с 494 до 366 (2048) и 241 ток/с (1024).
- `--checkpoint-min-step 0` на результат не влияет.
- Кэш промптов в RAM (`--cache-ram`, по умолчанию 8 GB) работает: после вытеснения слота другой работой общий префикс восстанавливается.
- «Затравочный» запрос с одной общей частью промпта ничего не добавляет: контрольная точка на начале сообщения пользователя и так есть.

Вывод: достаточно, чтобы у всех ролей совпадало всё до сообщения задачи — системный текст и инструменты.

## Что изменено в NETRUNNER

`electron/main/services/opencode.ts`:
- **Один системный промпт для всех ролей.** Роль и её правила переехали в начало сообщения задачи: `[ROLE: ARCHITECT] You are ARCHITECT. …` (`roleHeader`). В ленте NETRUNNER этот заголовок не показывается.
- **Один набор инструментов для всех ролей:** в конфигурации OpenCode у каждой роли `edit: ask`, `bash: ask`.
- **Ограничения ролей теперь проверяет NETRUNNER** (`rolePolicyReply`). Запрос правки файла от ARCHITECT, REVIEWER или OPERATOR и запрос команды от ARCHITECT отклоняются автоматически — до вопроса оператору и до любого разрешения «ВСЕГДА». Под-агенты (инструмент `task`) наследуют роль родительской сессии. Если роль сессии неизвестна, запрос, как и раньше, идёт оператору.
- Общая часть промптов ролей стала **20 828 символов из ~21 000** (99 %).

Отдельно (этап 0): MoE-модели запускаются на 8 потоках CPU вместо 16.

## Результат: тот же агентный прогон до и после

Один и тот же прогон (`npm run test:smoke` с агентной моделью Coder-Next), полные логи сервера, разбор — `tools/nsc/prompt-reuse.mjs`.

| | Этап 0 (до) | Этап 1 (после) |
|---|---|---|
| Токенов промпта всего | 46 242 | 59 695 |
| Из них пересчитано | 57.5 % | **17.7 %** |
| Время чтения промптов | 147 с | **53 с** (−64 %) |
| Начала шагов 2–4: прочитано токенов | 7134 + 7500 + 6995 | **614 + 1078 + 1347** |
| Начала шагов 2–4: время | 28.7 + 28.5 + 27.4 = 84.6 с | **5.2 + 6.1 + 6.3 = 17.6 с** (−79 %) |
| Время шагов ARCHITECT / CODER / DEBUGGER / REVIEWER | 103 / 49 / 42 / 44 с | **31 / 39 / 19 / 23 с** |
| Конвейер целиком (4 шага) | 238 с | **112 с** (−53 %) |
| Скорость генерации в агентах | 18–21 ток/с | 22–24 ток/с |
| CPU системы, пик | 80 % | **42 %** |
| RAM системы, пик | 63.7 GB | 59.5 GB |
| Проверки smoke | 60 / 60 | 60 / 60 |

Честные оговорки:
- Ускорение складывается из двух правок. Ускорение начал шагов 2–4 (84.6 → 17.6 с) — заслуга этапа 1. Генерация (+15 %) и первый шаг (54 → 25 с: тот же объём промпта прочитан быстрее, меньше давление на RAM) — частично от 8 потоков, частично разные условия прогона.
- Прогон один, задача smoke небольшая. Все 4 шага завершились, проверки smoke те же 60 из 60. ARCHITECT и REVIEWER файлы не правили (их инструменты: только `read`). Попыток запрещённых действий в этом прогоне не было, поэтому автоматический отказ проверен юнит-тестом, а не вживую.
- RAM по-прежнему выше 50 % — это вопрос модели (45 GiB), а не этого этапа.
