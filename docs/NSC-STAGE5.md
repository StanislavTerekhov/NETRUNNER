# NSC, этап 5 — свой форк llama.cpp

Дата: 2026-11-04. Данные — `%USERPROFILE%\NETRUNNER\nsc\stage5\`, исходники форка — `%USERPROFILE%\NETRUNNER\fork\`.

## Что поставлено

С вашего согласия поставлены:
- **VS Build Tools 2022:** C++, Windows SDK 26100, CMake и Ninja.
- **CUDA Toolkit 13.5** — та же мажорная версия CUDA 13, что у официальной сборки b12020. Видеодрайвер не менялся (621.01).

Исходники — тег b12020 (коммит 0ec4027, тот же, что у рабочей сборки). Сборка: `tools/nsc/build-llama.cmd`, MSVC + CUDA, только sm_86 (RTX 3060).

**Своя сборка медленнее официальной на 4–5 %:** 20.7 против 21.8 ток/с без кэша, 23.9 против 24.9 с кэшем. Официальная собрана Clang 20, моя — MSVC. Поэтому форк сравнивался со своей же обычной сборкой.

## Изменения форка

`tools/nsc/llama-moe-cache-stats.patch`, файл `src/llama-moe-cache.cpp`. Всё включается переменными окружения, без них поведение обычное.

- `LLAMA_MOE_CACHE_STATS=N` — каждые N токенов печатает долю попаданий, объём подкачки и время ожидания в кэше. В обычной сборке статистика печатается только при штатном завершении сервера, поэтому на этапе 4 её не было видно.
- `LLAMA_MOE_CACHE_FREQ=<файл>` — сколько раз выбран каждый эксперт.
- `LLAMA_MOE_CACHE_PIN=<файл>` — закреплённый набор экспертов (идея этапа 5): загружаются при старте и никогда не вытесняются; `LLAMA_MOE_CACHE_PIN_FRAC` — доля кэша под него, по умолчанию половина.

## Что показала статистика

Coder-Next, кэш 6 GB (13 % всех экспертов), задачи базовой линии:

| Задача | Попадания | Подкачка на токен | Ожидание в кэше на токен |
|---|---|---|---|
| Русский текст | 85–88 % | 110–140 MiB | 13–17 мс |
| Код | 70–78 % | 190–270 MiB | 30–50 мс |
| После длинного контекста | 57–69 % | 270–400 MiB | 30–50 мс |

**Узкое место — не политика кэша, а скорость подкачки.** Эксперты лежат в памяти, отображённой из файла модели (mmap). CUDA копирует из такой памяти через промежуточный буфер: около 7 GB/с, и копия фактически синхронная.

## Главная находка: веса в закреплённой памяти

С `-lm none` llama.cpp читает веса не через mmap, а в закреплённую память CUDA (pinned). Это есть в официальной сборке, форк не нужен.

| Coder-Next, кэш 6 GB | Генерация | Русский / код / после длинного контекста | Ожидание в кэше |
|---|---|---|---|
| Без кэша (как у агентов сейчас) | 21.8 | 20.9 / 21.4 / 23.2 | — |
| Кэш, mmap (этап 4) | 24.2–24.9 | 31 / 23 / 19 | 13–50 мс |
| **Кэш, pinned** | **30.3–30.5 (+40 %)** | **38.7 / 28.6 / 24.1** | **1.7–3 мс** |

- Попадания те же (одни и те же числа до процента), но подкачка стала асинхронной и быстрее: около 10 GB/с в среднем.
- Теперь кэш выигрывает и после длинного контекста. На этапе 4 там был проигрыш.
- **Цена — загрузка модели:** около 100 с вместо 6–9 с. Файл читается за 15 с, остальное время уходит на закрепление 45 GB памяти. RAM занято столько же, сколько с mmap: около 55 из 64 GB.
- Официальная сборка даёт то же самое (30.5 ток/с).

## Агенты

Статистика на настоящем конвейере агентов: попадания всего **60–75 %**, подкачка около 300 MiB на токен. Агенты задействуют 20 662 эксперта из 24 576. Даже самые частые 3 200 экспертов (весь кэш) покрыли бы только 52 % обращений.

Короткий агентный тест (`test/nsc/stage5-agent-loop.live.test.ts`) состоит из настоящего системного промпта и инструментов агентов и шести ходов с результатами инструментов по 120–1300 токенов:

| Вариант | Весь цикл | Чтение промптов | Генерация |
|---|---|---|---|
| Как сейчас | 46.8 с | 37.3 с | 23.6 |
| Кэш, pinned | 47.0 с | 33.6 с | 24.4 |
| Кэш, pinned, закреплённый горячий набор (форк) | 41.6 с | 31.5 с | 24.4 |
| Кэш, pinned, батчи < 256 токенов на CPU (`GGML_OP_OFFLOAD_MIN_BATCH=256`) | 38.6 с | 28.5 с | 25.1 |
| Кэш, pinned, 8 экспертов (этап 6) | 39.9 с | 29.8 с | 29.3 |
| Как сейчас, батчи < 2048 на CPU | 39.6 с | 29.9 с | 21.9 |

Здесь по одному прогону на вариант. Чтение одного и того же промпта колеблется на ±15 %, поэтому решение принималось по настоящему конвейеру, три прогона подряд:

| Конвейер агентов (4 шага) | Шаги | Чтение промптов | Генерация | Проверки |
|---|---|---|---|---|
| Как сейчас | 109 с | 58.3 с (9 запросов) | 39.0 с | 60/60 |
| Батчи < 2048 на CPU | 118 с | 59.7 с (10) | 46.1 с | 60/60 |
| Кэш, pinned, батчи < 256 на CPU | 122 с | 54.3 с (11) | 51.4 с | 58/60 |
| (ранее) Кэш, pinned | 96 с | — | — | 60/60 |
| (ранее) Кэш, pinned, форк со статистикой | 153 с | — | — | 59/60* |

\* Не прошла проверка плана размещения в MODEL VAULT: в сборке форка нет `llama-fit-params.exe`.

Одна и та же настройка (кэш, pinned) дала 96 и 153 с. Так выглядит разброс конвейера.

**На реальном конвейере выигрыша нет.** Агенты от прогона к прогону делают разное число запросов и пишут разный объём, и этот разброс больше разницы между настройками. Скорость генерации по шагам: 22–26 ток/с с кэшем против 22–24 без него.

В прогоне с кэшем не прошли две проверки интерфейса: переключение на русский и обратно, и список разрешений ALWAYS. На следующем прогоне, без кэша, все 60 прошли. С сервером модели эти проверки не связаны. Повторно этот вариант я не прогонял.

## Решение

| | Итог |
|---|---|
| Закреплённый набор горячих экспертов (форк) | не даёт выигрыша: динамический кэш и так держит частых экспертов, а рабочий набор агентов шире кэша. Не используется |
| Статистика кэша (форк) | показала, где теряется время. Остаётся как инструмент замеров |
| Своя сборка вместо официальной | медленнее на 4–5 % (MSVC против Clang) и не даёт выигрыша. Приложение остаётся на официальной b12020 |
| **Кэш экспертов + веса в pinned-памяти** | **+40 % генерации на чате.** Включено: если тюнер выбирает кэш, добавляется `-lm none` |
| Порог переноса на GPU (`GGML_OP_OFFLOAD_MIN_BATCH`) | на коротком тесте −18 %, на реальном конвейере не подтвердился. Не включается |

Что изменилось в NETRUNNER: `serverArgs` с профилем `moeCacheMib` теперь добавляет `-lm none`. Тюнер по-прежнему решает, включать ли кэш, замером. Для модели агентов он меряет агентный тест. Если MoE-модель служит моделью чата, тюнер теперь найдёт выигрыш около +40 % вместо +22 %. Плата — загрузка модели около 100 с.

**Отменено 2026-11-06 (NSC-ME, фаза 5, `docs/NSC-ME.md`).** С `-lm none` Coder-Next занимает 76 из 77 GB commit, Windows расширяет файл подкачки, другим программам остаётся ~7 GB, возврат после выгрузки — ~100 с. По решению пользователя кэш экспертов работает без `-lm none`, на mmap (~+22 % на чате вместо +40 %).
