# NSC, этап 0 — замеры, которые могли опровергнуть гипотезу

Дата: 2026-11-03. Машина: Ryzen 9 5950X, 64 GB DDR4, RTX 3060 12 GB. llama.cpp b12020 CUDA.
Все числа сняты на этой машине; исходные данные — `%USERPROFILE%\NETRUNNER\nsc\stage0\`.

Инструменты (в репозитории):
- `tools/nsc/sampler.mjs` — раз в секунду: загрузка GPU, VRAM, мощность GPU, PCIe rx/tx (`nvidia-smi dmon`), CPU и RAM системы, CPU и RAM процессов NETRUNNER.
- `test/nsc/stage0-baseline.live.test.ts` — базовая линия трёх моделей на одних и тех же задачах (`NETRUNNER_LIVE=1`).
- `tools/nsc/expert_stats.py` — статистика выбора экспертов Coder-Next по данным `llama-imatrix`.
- `NETRUNNER_SERVER_LOG_DIR` в `electron/main/services/llamacpp.ts` — полный лог llama-server в файл (только для замеров, по умолчанию выключено).

## 1. Базовая линия

Задачи: короткий ответ по-русски, генерация кода, длинный контекст (~15 тыс. символов кода + вопрос). temperature 0, кэш промпта выключен, без thinking, первый прогон — прогрев, не считается.

| | Qwen 27B IQ3_XXS | Coder-Next Q4_K_M | netrunner-v3 4B |
|---|---|---|---|
| Размер весов | 10.2 GiB | 45.1 GiB | 2.6 GiB |
| Генерация, ток/с | 12.4–12.9 | 17.9–21.9 | 81–85 |
| Чтение длинного промпта, ток/с | 552 | 449 | 3141 |
| Загрузка модели | 30 с | 92 с | 9 с |
| VRAM (из 12 GB) | 11.9 GB | 11.5 GB | 4.8 GB |
| Загрузка GPU при генерации | 52–56 % | 37 % | 93–95 % |
| CPU системы при генерации | ~57 % | ~58 % | ~9 % |
| RAM процессов NETRUNNER | 12 GB | 21 → 44 GB | 4 GB |
| Энергия GPU на токен | 10.0 Дж | 2.2 Дж* | 2.0 Дж |

Простой без моделей: CPU 6 %, RAM 17.1 GB, VRAM 1.5 GB, GPU 16 Вт.

\* Для Coder-Next основную работу делает CPU (эксперты в RAM), а мощность CPU на этой машине измерить нечем — сравнивать «2.2 Дж» с 27B нельзя, реальная цифра выше.

Вывод: обе большие модели упираются не в GPU, а в CPU и память (GPU ждёт половину времени). Узкое место — перекачка весов из RAM. Это ровно та точка, куда целит NSC.

## 2. Повторяемость промптов (агентный конвейер)

Прогон агентного конвейера NETRUNNER на Coder-Next (9 запросов к модели), разбор по логу llama-server:

- Внутри одного шага агента следующий запрос переиспользует 96–99 % уже посчитанного промпта — кэш llama.cpp здесь уже работает.
- Каждый **новый шаг** конвейера (новая роль/сессия) пересчитывает промпт **целиком**: 4.6–7.5 тыс. токенов, 27–54 с на шаг.
- Итого 46 246 токенов промпта, из них пересчитано 57.5 %. Чтение промптов заняло 147 с, из них 138 с — на старте новых шагов. Генерация — ~83 с.

Порог «меньше ~20 % общих токенов → этап 1 опционален» не сработал: пересчитывается больше половины, и это больше половины времени ожидания. Какая доля этих промптов действительно общая между ролями (системный промпт, описания инструментов) — пока не измерено; для этого нужен захват самих промптов, это первый шаг этапа 1.

## 3. Эксперты Coder-Next

Модель: 48 слоёв × 512 экспертов, на токен 10 экспертов на слой; один эксперт ≈ 1.82 MiB, все эксперты — 43.6 GiB. Корпус — наши реальные данные: логи агентов, русская документация проекта, код проекта (420 тыс. символов).

На том же корпусе, на котором выбирали (оптимистичная оценка):
- 50 % токенов обслуживают в среднем 55 экспертов из 512, 80 % — 167; равномерность 0.87 (1.0 = идеально равномерно).
- Если держать в VRAM самые частые эксперты: 1 GB → 23 % работы, 2 GB → 34 %, 4 GB → 48 %, 6 GB → 58 % (случайный набор: 2.3 / 4.6 / 9.2 / 13.8 %).

Стоп-критерий «выбор почти равномерный» **не сработал**: концентрация в 5–7 раз выше случайной.

Проверка, держится ли набор, выбранный заранее (60 фрагментов по 512 токенов на каждую часть):

| Набор выбран на → проверен на | 1 GB | 2 GB | 4 GB | 6 GB |
|---|---|---|---|---|
| текст → текст | 29 % | 41 % | 54 % | 64 % |
| код → код (тот же код) | 29 % | 41 % | 56 % | 66 % |
| текст → код | 6 % | 12 % | 20 % | 27 % |
| код → текст | 6 % | 10 % | 18 % | 25 % |
| **код, файлы A → код, файлы B** | 27 % | 39 % | 55 % | 64 % |
| **код, файлы B → код, файлы A** | 29 % | 41 % | 56 % | 65 % |

Последние две строки — главная проверка. Код проекта поделён на две половины по разным файлам (49 файлов, ~160 тыс. символов в каждой). Набор, выбранный на одних файлах, на других работает почти так же, как на своих: 39–41 % против 40–42 % при 2 GB. Значит, горячий набор держится внутри типа работы. Между типами работы (текст ↔ код) он не держится: там выигрыш падает в 3–4 раза. Отсюда вывод: нужен свой набор на каждый режим (агенты-код и чат-текст), а не один общий.

## 4. Ресурсы и требование «минимум 50 % мощностей свободно»

Во время агентного прогона Coder-Next:
- RAM системы до 63.7 из 63.9 GB, процессы NETRUNNER до 50.5 GB; больше половины RAM занято 75 % времени.
- VRAM занята больше чем наполовину 100 % времени.
- PCIe: в среднем 4 GB/с, пик 20.5 GB/с.
- GPU в среднем 40 %, CPU в среднем 23 %, пик 80 %.
- Чтение промпта в агентах — 85–260 ток/с против 449 в чистом замере. Вероятная причина — нехватка RAM (система вытесняет страницы весов). Это первый найденный пример «обратной интерференции». **Исправлено на этапе 2:** не подтвердилось. Coder-Next не замедлялся и при 3 GB, и при 1.2 GB свободной RAM. Медленное чтение было на первых запросах после загрузки модели (холодные страницы) и на длинных промптах агентов (см. docs/NSC-STAGE2.md).

Что значит бюджет 50 % на этой машине: VRAM ≤ 6 GB, RAM ≤ 32 GB, CPU ≤ 50 %, GPU ≤ 50 %.

| Модель | VRAM | RAM | CPU | GPU | Влезает в 50 %? |
|---|---|---|---|---|---|
| 4B | 4.8 GB ✓ | 4 GB ✓ | 9 % ✓ | 94 % ✗ | почти: только загрузка GPU |
| 27B IQ3 | 11.9 GB ✗ | 12 GB ✓ | 57 % ✗ | 55 % ✗ | нет |
| Coder-Next | 11.5 GB ✗ | 21–50 GB ✗ | 58 % ✗ | 37 % ✓ | нет |

**Честно о конфликте «50 % свободно» и «без потери скорости»:**
- Coder-Next весит 45 GiB. В 6 GB VRAM + 32 GB RAM он не помещается физически: остаток придётся читать с диска, генерация упадёт в разы. При бюджете 50 % без потери скорости Coder-Next на этой машине работать не может — нужен либо меньший квант (ориентировочно Q3 ≈ 35–38 GiB тоже не влезает, Q2 ≈ 27–29 GiB влезает, но с потерей качества, которую надо мерить), либо исключение из правила для агентного режима.
- 27B: при ограничении VRAM до 6 GB около 4 GB весов уходят в RAM. Генерация на этой модели и так ограничена памятью; оценка была 6–8 ток/с, замер (раздел 6) — 3.7 ток/с.
- CPU ≤ 50 %: замер (раздел 6) — 8 потоков вместо 16 ничего не стоят, а Coder-Next на 8 потоках даже быстрее.
- GPU ≤ 50 % для 4B: ограничить «загрузку» GPU можно только снижением лимита мощности видеокарты (это системная настройка — только вы) или искусственными паузами между токенами (= прямая потеря скорости).

Итог: требование 50 % выполнимо без потерь только для 4B (кроме загрузки GPU). Для 27B и Coder-Next оно стоит скорости — сколько именно, в разделе 6.

## 5. Решения по этапам

| Этап | Решение | Почему |
|---|---|---|
| 1. Слоты/переиспользование префиксов | **Делать** | 57.5 % промпта пересчитывается, 138 с из 147 с ожидания — на старте шагов. Даже частичное переиспользование даёт десятки секунд на задачу. Первым шагом — захват промптов и замер реально общей части. |
| 2. Монитор обратной интерференции | **Делать** (дёшево) | Сэмплер готов. (Предполагаемый случай с нехваткой RAM на этапе 2 не подтвердился; реальные помехи — занятый CPU и чужая VRAM.) |
| 3. Автотюнер с откатом | Отложить до результатов 1–2 и решения по 50 % | Ему нужны правила, а правила зависят от бюджета ресурсов. |
| 4. Горячие эксперты в VRAM (`-ot`) | **Условно** | Гипотеза подтверждена по данным: заранее выбранный набор на 2 GB закрывает ~40 % работы экспертов на новом коде (случайный — 4.6 %). Верхняя оценка — до ~1.5× к генерации Coder-Next, если 40 % чтений экспертов уйдут с CPU на GPU. Но VRAM сейчас занята на 11.5 GB, а при бюджете 50 % места для экспертов нет вовсе. Сначала решение по бюджету, потом освобождение VRAM (меньше контекст или квантованный KV-кэш) и замер реального выигрыша. Наборы — отдельно для кода и для текста. |
| 5. Динамический кэш экспертов | Не сейчас | Нужен свой форк llama.cpp + VS Build Tools + CUDA Toolkit (не установлены). Смысл есть только если этап 4 покажет пользу. |
| 6. Приближённый режим | Не сейчас | Риск для качества; только после 1–4 и только с проверкой бенчмарками FORGE. |

## 6. Цена правила «50 % свободно» (замер 2026-11-04)

**Решение пользователя (2026-11-04): скорость важнее, правило не применяется.** Из него взяты только бесплатные улучшения: 8 потоков для MoE.

`test/nsc/stage0-budget.live.test.ts`, данные — `budget.json`, `budget-coder-next.json`. Те же задачи, что в базовой линии. VRAM ограничивается штатным механизмом llama.cpp (`--fit-target`: сколько VRAM оставить свободной), CPU — числом потоков (`-t/-tb`). Скорость генерации — среднее по трём задачам.

| Модель, конфигурация | Генерация, ток/с | Длинный промпт, ток/с | VRAM NETRUNNER | CPU NETRUNNER | RAM NETRUNNER |
|---|---|---|---|---|---|
| **27B** как сейчас | 12.7 | 552 | 10.5 GB | 46 % | 12 GB |
| 27B, VRAM ≤ 6 GB | 3.7 (**−71 %**) | 432 | 6.3 GB | 51 % | 13 GB |
| 27B, VRAM ≤ 6 GB, 8 потоков | 3.7 (−71 %) | 426 | 6.3 GB | 25 % | 13 GB |
| 27B, VRAM ≤ 6 GB + MTP | 5.1 (−60 %) | 350 | 6.3 GB | 50 % | 14 GB |
| **Coder-Next** как сейчас | 19.9–20.0 | 454–460 | 10.2 GB | 42 % | 44 GB |
| Coder-Next, 8 потоков | **21.3 (+7 %)** | 461 | 10.2 GB | **21 %** | 44 GB |
| Coder-Next, VRAM ≤ 6 GB | 16.1–17.0 (−17 %) | 429 | 6.0 GB | 43 % | 44 GB |
| Coder-Next, VRAM ≤ 6 GB, 8 потоков | 18.0 (**−10 %**) | 431 | 6.1 GB | 22 % | 43 GB |
| **4B** как сейчас | 83.2 | 3077 | 3.4 GB | 3 % | 4 GB |
| 4B, VRAM ≤ 6 GB, 8 потоков | 83.9 (0 %) | 3133 | 3.5 GB | 3 % | 4 GB |

Coder-Next прогнан дважды: два прогона расходятся не больше чем на 1 ток/с. Выигрыш 8 потоков повторился в обоих (+5–7 %).

Что это значит:
- **27B** с правилом теряет 71 % скорости генерации, а со своей MTP-головой — 60 %. Плотная модель в 6 GB не помещается: на каждый токен ~4 GB весов читаются из RAM. Обойти это можно только моделью меньше: например, 4B (84 ток/с) или 27B в более сильном кванте (качество придётся мерить).
- **Coder-Next** по VRAM и CPU выполняет правило за −10 % скорости. По RAM — нет: он держит ~44 GB (69 % из 64 GB), а модель весит 45 GiB. Ограничить RAM средствами llama.cpp нельзя: превышение означает чтение весов с диска.
- **CPU:** 16 потоков на Coder-Next — это лишняя нагрузка. 8 потоков дают половину нагрузки на CPU и +7 % скорости: генерация упирается в память, и лишние потоки только мешают друг другу. Это улучшение без минусов, его можно внести в NETRUNNER независимо от правила 50 %. Для 27B число потоков на скорость не влияет.
- **4B** выполняет правило бесплатно. Нарушается только загрузка GPU (83–87 %), но её можно ограничить только лимитом мощности видеокарты — это системная настройка, её меняете только вы.
- Загрузка моделей в повторных прогонах — 3–8 с вместо 9–92 с, потому что файлы уже лежат в кэше Windows. Для сравнения скорости это не важно.

**Применено (2026-11-04):** serverArgs даёт MoE-моделям четверть логических CPU (-t/-tb, на этой машине 8). Живая проверка Coder-Next с аргументами NETRUNNER: 21.4 ток/с, длинный промпт 454 ток/с, CPU NETRUNNER 21 %. Один из трёх прогонов был испорчен посторонней нагрузкой (18.8 ток/с, промпт 208) и повторён.
