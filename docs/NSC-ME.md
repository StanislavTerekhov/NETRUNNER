# NSC-ME — эластичная память моделей: план исследований и доработки

Дата: 2026-11-05. Основа — гипотеза NSC-ME 0.4 (H1–H7) и замеры этапов NSC 0–6.
Данные фаз — `%USERPROFILE%\NETRUNNER\nsc\me\phase<N>\`.

Цель: отдавать RAM и VRAM другим программам при заданной цене по скорости и времени
возврата, не теряя готовности модели. Свой контроллер внутри модели (H7) — возможный
итог, а не обязательная часть: сначала стандартные средства llama.cpp и Windows,
потом политика на уровне приложения, и только потом — код форка.

Каждая фаза заканчивается решением. Дорогие фазы идут последними и начинаются,
только если их оправдали дешёвые.

## Часть 1. Исследования

фаза 8 — 1–2 дня и только при необходимости.

### Правила замеров

- Фиксированные входы; конфигурации чередуются (ABAB), порядок записывается.
- Prefill, decode, время задачи и Idle/Resume — отдельные метрики со своей дисперсией.
  Число прогонов считается по разбросу фазы 0 и минимальной значимой разнице.
- p95 — только по задержке токенов (сотни наблюдений за прогон), не по времени задачи.
- Состояние файлового кэша записывается. «Холодный» — только если это подтверждено.
  SysMain может сам подгружать файлы в standby.
- Сжатие памяти Windows учитывается отдельно: частные страницы (KV, pinned) сжимаются,
  файловые (веса через mmap) — нет.
- Форк сравнивается с форком без изменений: своя сборка (MSVC) на 4–5 % медленнее
  официальной (Clang).

## Результаты

### Фаза 0 — исходные показатели (2026-11-05)

Замер: `test/nsc/me-phase0.live.test.ts`, данные — `nsc\me\phase0\`. Каждая модель так, как её
запускает NETRUNNER (27B — ubatch 1024, 4B — MTP по итогам этапа 3; Coder-Next — по умолчанию,
65K × 2 слота). Две загрузки × 5 повторов; в каждом повторе prefill фиксированного промпта
4264 токена (без кэша промпта) и генерация 300 токенов потоком; порядок чередуется.

**Окружение.** Windows 11 Home 26100, Ryzen 9 5950X, 64 GB, RTX 3060 12 GB (драйвер 621.01),
llama.cpp b12020 (Clang 20.1.8). Схема питания «Сбалансированная». SysMain работает.
**Модели лежат на C: — Samsung 870 EVO, SATA SSD** (паспортно ~0.55 GB/с). NVMe в системе нет;
второй диск — HDD. В гипотезе стояли 4 GB/с — это в ~7 раз выше реального диска.

| Модель | Prefill, ток/с | Генерация, ток/с | p95 промежутка, мс | Загрузка: первая / повторная |
|---|---|---|---|---|
| Coder-Next | 614 (CV 1.1 %) | 22.2 (CV 0.8 %) | 51.4 | 92 с / 8.3 с |
| Qwen 27B IQ3 | 538 (CV 0.2 %) | 15.1 (CV 0.2 %) | 69.4 | 31 с / 7.8 с |
| netrunner-v3 4B | 2802 (CV 0.8 %) | 131.1 (CV 0.7 %) | 26.8 | 9.4 с / 3.7 с |

- **Разброс самого движка мал: 0.2–1.1 %**, и между двумя загрузками средние совпадают
  (22.3/22.1, 15.1/15.1, 130.8/131.4). Разброс ±15 % этапа 5 давал не llama-server, а
  поведение агентов (разное число и длина запросов).
- **Сколько прогонов нужно:** при CV ≤ 1.1 % три прогона на конфигурацию уверенно видят
  разницу ≥ 3 % (мощность 80 %, α = 0.05); пять — ≥ 2 %. Для допуска 10 % хватает трёх.
  Время агентской задачи остаётся шумным — только вспомогательная метрика.
- **Время до первого токена** шумит в относительных числах (CV 18–32 % у 27B и 4B), но это
  десятки миллисекунд; первичной метрикой оно не будет.
- **Первая загрузка против повторной — в 3–11 раз дольше.** Повторная идёт из standby
  (8 с для 45 GB), первая дочитывала с SATA SSD (Coder-Next — 92 с). Для H3/H4 это означает:
  если память модели реально заняла другая программа, возврат будет ближе к 92 с, чем к 8 с.
  Точно — в фазе 1.
- **Частная память (commit) после загрузки:** Coder-Next +14.7 GB, 27B +13.4 GB, 4B +9.4 GB —
  это не веса через mmap, а буферы и контекст; её Windows отобрать не может. Что из неё что —
  разобрать в фазе 3.
- Температура GPU 45–63 °C, скорость стабильна — тепловых эффектов нет. Сжатие памяти
  Windows — до 0.4 GB, на замеры не влияет.

**Что это меняет в плане.** Скорость диска — главный параметр H3 и H4, и она на порядок ниже
заложенной. Прогноз по H3 («≥ 16 GB за ≤ 10 с») ухудшается: 16 GB с этого диска — около 30 с.
H2 при таком диске практически закрыта уже сейчас (бюджет промахов ~0.3 %). Холодные замеры
фазы 1 требуют действия пользователя: перезагрузка, отключение SysMain или очистка standby.

### Фаза 1 — диск и копирование RAM → GPU, тёплая часть (2026-11-05)

Инструменты (наш код): `tools/nsc/diskbench.c`, `tools/nsc/h2dbench.cu`, сборка —
`tools/nsc/build-bench.cmd`. Данные — `nsc\me\phase1\disk.jsonl`, `h2d.jsonl`. Файл —
часть 3 Coder-Next (14.5 GB), блок = один эксперт (1.64 MiB), 800 блоков, 3 повтора. Модели не загружены.

**Чтение с диска.** Чтение с флагом NO_BUFFERING идёт мимо файлового кэша, поэтому это
настоящая скорость накопителя без перезагрузки.

| Способ | Скорость | На один эксперт | Примечание |
|---|---|---|---|
| Последовательно, мимо кэша | 0.56 GB/с | — | 3 из 3 совпадают |
| Случайные эксперты, мимо кэша, 1 запрос | 0.52 GB/с | 3.3 мс | |
| Случайные эксперты, мимо кэша, 4 / 16 запросов | 0.56 GB/с | — | Очередь не помогает: SATA уже упёрт в предел |
| ReadFile через кэш, данных в кэше нет | 0.51 GB/с | 3.5 мс | |
| ReadFile через кэш, повторно | 11.5–12.5 GB/с | 0.14 мс | |
| mmap, промах с диска | 0.34 GB/с | 5.5 мс | 1 из 3 повторов; в двух других регионы оказались в standby |
| mmap, страницы в standby | 5.0–5.2 GB/с | 0.35 мс | Мягкие страничные промахи |

**Копирование RAM → GPU** (блоки по 1.64 MiB, 1 GiB, 3 повтора по 3 раза, разброс < 3 %):

| Способ | Скорость | На эксперт |
|---|---|---|
| Из обычной памяти (`cudaMemcpy`, как кэш экспертов с mmap) | 8.0–8.3 GB/с | 210 мкс |
| Из закреплённой памяти, асинхронно (как с `-lm none`) | 13.2 GB/с | 130 мкс |
| **Через закреплённое кольцо из 2 / 4 / 8 слотов (H5)** | **11.5–12.0 GB/с** | 145 мкс |
| Копия CPU из обычной памяти в обычную | 17 GB/с | 100 мкс |

**Выводы.**
- **Диск — 0.52–0.56 GB/с при любом способе чтения.** Это потолок для всего, что
  возвращается с накопителя. 16 GB — около 30 с, весь Coder-Next — около 85 с. Это совпадает
  с первой загрузкой фазы 0 (92 с). Из standby тот же объём возвращается в 10–20 раз быстрее.
- **H2 по этому диску закрыта.** Бюджет промахов RAM при −10 % генерации:
  0.005 × 0.54 / 0.8 ≈ **0.34 %** нужных байтов. Каждая пачка промпта трогает почти все
  эксперты. Решение: H2 не разрабатывается. Пересмотр — только при переносе моделей на NVMe.
- **H6 под вопросом, но выигрыш ограничен диском.** Явное чтение быстрее промахов mmap в
  ~1.5 раза (0.52 против 0.34 GB/с). Это ровно порог плана, но замер один и не подтверждён как
  холодный. Даже при подтверждении H6 сократит возврат 16 GB только с ~47 до ~30 с. Нужен
  холодный повтор.
- **H5 предварительно подтверждается.** Кольцо из 2 слотов (3.4 MB закреплённой памяти
  вместо 45 GB) даёт 89–91 % скорости полностью закреплённых весов и в 1.45 раза быстрее
  обычного копирования. Оговорки: замер синтетический — GPU ничем не занят, CPU не делит
  время с потоками модели, одна очередь копирования. Окончательно — только в форке (фаза 8).
- Для У4 и H3 это значит, что конфликт «быстро или эластично» решаем: скорость `-lm none`
  почти без закреплённой памяти, а возврат после простоя ограничен диском, а не закреплением.

### Фаза 1 — холодная часть (2026-11-05, после перезагрузки)

Скрипт `tools/nsc/me-phase1-cold.sh`, данные — `nsc\me\phase1\cold.jsonl`, `cold-state.json`,
`cold-load.log`. Через 0.7 мин после загрузки Windows: в standby ~3 GB, llama-server не запущен,
SysMain работает. Файл — часть 2 Coder-Next. **Холод подтверждён замером:** во всех трёх
проходах mmap медиана на эксперта 4.6–5.7 мс. Из standby было бы ~0.35 мс.

| Способ, холодный файл | Скорость (3 прохода) | Медиана на эксперта |
|---|---|---|
| mmap (страничные промахи) | 0.28 / 0.37 / 0.37 GB/с | 4.6–5.7 мс, хвост до 111 мс |
| ReadFile через кэш | 0.56 / 0.64 / 0.78 GB/с | 2.4–3.5 мс |
| Мимо кэша (тёплая часть, для сравнения) | 0.52–0.56 GB/с | 3.3 мс |
| **Полная загрузка Coder-Next llama.cpp** | **82 с** (45 GB ≈ 0.55 GB/с); повторно из standby — 8.8 с | — |

В третьем проходе ReadFile часть случайных экспертов совпала с уже прочитанными, отсюда 0.78.

**Выводы.**
- **Явное чтение быстрее промахов mmap в 1.65 раза** (0.56 против 0.34 GB/с, медиана) и с
  гораздо более коротким хвостом. Порог H6 (≥ 1.5×) пройден.
- **Но полная загрузка llama.cpp уже идёт на пределе диска** (82 с ≈ 0.55 GB/с). H6 даёт выигрыш
  только при ленивом возврате, когда веса подтягиваются промахами по ходу работы. Для возврата
  «загрузить модель целиком» улучшать нечего. Решение: H6 не разрабатывается отдельно. Её
  вывод (читать явно и крупно, а не промахами) — требование к У3 и к возможной фазе 8.
- **Цена холодного возврата для H3 и H4:** весь Coder-Next — 82 с, против 8.8 с из standby.
  Порог H3 «16 GB за ≤ 10 с» на этом диске недостижим (16 GB ≈ 29 с). Пороги H3 надо
  пересмотреть под диск или считать H3 выполненной только при тёплом возврате.
- Скорость сразу после холодной загрузки (одна загрузка, по одному повтору: генерация 20.0 и
  25.1 ток/с) — шум первых минут после старта Windows. Для выводов не используется.

### Фаза 2 — инструменты (2026-11-05)

| Инструмент | Что делает |
|---|---|
| `tools/nsc/memconsumer.c` — `ram <GiB> <проходов>` | Берёт и записывает частную память, затем повторяет фиксированный проход: чтение всех слов и запись по слову на страницу. По каждому проходу: время, GB/с, страничные промахи, рабочий набор. `--hold-seconds` — работать рядом с моделью, `--trim-after` — самопроверка |
| `tools/nsc/memconsumer.c` — `cpu <потоков> <проходов>` | Фиксированная целочисленная нагрузка; время прохода — для соревнования за CPU |
| `tools/nsc/vramconsumer.cu` — `<GiB> <проходов>` | `cudaMalloc` по 256 MiB и фиксированный kernel чтения-записи; пропускная способность по проходам |
| `tools/nsc/stats.mjs` | Эффект B против A в % с bootstrap-интервалом 95 %; проверка «весь интервал внутри допуска»; число прогонов по разбросу; чередование ABBA. Юнит-тест `test/nsc-stats.test.ts` |

RAM Consumer написан на C, а не на Node, как было в плане: так в замере нет сборщика мусора
V8 и видны настоящие страничные промахи процесса. Данные самопроверки — `nsc\me\phase2\`.

**Самопроверка — инструменты видят деградацию, когда она точно есть:**
- **RAM, 16 GiB:** обычный проход — 23.8 GB/с, 0 промахов. После сброса собственного рабочего
  набора (`EmptyWorkingSet`) следующий проход — **2.6 GB/с, 4.19 млн промахов** (все 16 GiB).
  Проход после него снова 23.7.
- **VRAM, 8 GiB:** 314–321 GB/с от прохода к проходу.
- **VRAM с перегрузкой:** A держит 6 GiB и работает, B берёт ещё 7 GiB (вместе 13 из 12). **B
  получает память без ошибки и видит в `cudaMemGetInfo` 11 GB «свободными»**, будто A нет.
  Драйвер молча вытесняет память A в системную: проход A в этот момент — **12.5 GB/с вместо
  318** (в 25 раз медленнее).
- **CPU, 16 потоков:** один — 0.60 с за проход, два таких одновременно — 0.68–0.71 с (+17 %).
  У 5950X 32 логических ядра, поэтому 16 + 16 в основном делят SMT. Чтобы увидеть соревнование
  с моделью, Consumer должен занимать столько потоков, сколько их у типичной сторонней программы.
- **Статистика:** две загрузки Coder-Next фазы 0 отличаются на −0.9 % (интервал −1.6…−0.2 %).
  Разница статистически значима, но целиком внутри ±2 %. **Правило решений: «интервал внутри
  допуска», а не одна значимость** — при CV ~1 % значимыми становятся и неважные различия.

**Что это меняет в плане.**
- **У5 (резерв VRAM) нельзя строить на `cudaMemGetInfo`:** на Windows он показывает бюджет
  своего процесса, а не реально свободную память карты. Резерв надо считать по `nvidia-smi`
  (занято всеми процессами) или по бюджету DXGI. NETRUNNER уже читает `nvidia-smi`
  (`hardware.ts`, `llamacpp.ts`) — источник для У5 есть. Переполнение не даёт ошибки ни одной
  программе — его видно только по падению скорости. Поэтому резерв обязателен, реакция после
  переполнения не работает.
- Тот же механизм объясняет −15 % чтения промптов на этапе 2 (вторая модель заняла VRAM).

### Фаза 3 — H4: выгрузка целых моделей (2026-11-05)

Замер: `test/nsc/me-phase3.live.test.ts`, данные — `nsc\me\phase3\`. Модели — как их запускает
NETRUNNER. Память — счётчики Windows и `nvidia-smi` (все процессы). Consumer'ы — RAM 16 GiB и
VRAM 6 GiB, рядом с простаивающей моделью и после её выгрузки.

**Как сейчас.** NETRUNNER держит одну чат-модель (слот `chat`) и модель эмбеддингов. Сам он их не
выгружает: модель остаётся, пока её не сменят. Смена чат-модели выгружает предыдущую.

| Модель | Держит, простаивая: VRAM / RAM (доступная) / commit | Выгрузка освобождает | Возврат из standby: загрузка + первый токен | Холодный возврат |
|---|---|---|---|---|
| Coder-Next | 10.1 GB / 13.0 GB / 15.0 GB | всё (10.1 / 13.7 / 15.2) | 7.8 с + 0.7 с | 93 с (первая загрузка после перезагрузки) |
| Qwen 27B | 10.6 / 11.8 / 14.0 | всё | 7.3 с + 0.5 с | 31 с |
| 4B | 4.0 / 4.2 / 9.4 | всё | 3.2 с + 0.13 с | 8.8 с |
| Эмбеддинги 0.6B | 1.7 / 1.1 / 2.3 | всё | 1.1 с | 2.2 с |

Возвраты из standby — 3 из 3 с разбросом < 2 %, кроме первого возврата Coder-Next (см. ниже).
Холодный возврат — первая загрузка в этом замере; для Coder-Next и 27B это подтверждено фазой 1.

**Находки.**

1. **Выгрузка отдаёт всё, что модель держала.** Доступная RAM, commit и VRAM возвращаются к
   исходным значениям в пределах 0.1–0.6 GB. Остатков нет.
2. **Возврат дешёвый, только пока файлы модели лежат в standby.** Пример из этого замера:
   Coder-Next выгружен, RAM Consumer занял и потрогал 16 GiB, и это вытеснило часть файлов
   модели. **Следующий возврат занял 37.4 с вместо 7.8.** Это ровно прогноз фазы 1: 16 GB с
   SATA ≈ 29 с плюс 8 с загрузки. Значит, цена возврата зависит от того, воспользовался ли
   кто-то освобождённой памятью. Это главный параметр H3 и фазы 5.
3. **Переключение 27B ↔ Coder-Next всегда холодное: 98–106 с на Coder-Next и 32 с на 27B**
   (3 из 3). Файлы двух моделей вместе (56 GB) не помещаются в standby при 64 GB RAM, и каждая
   смена вытесняет файлы другой модели. Это нынешнее поведение NETRUNNER при смене чат-модели.
   Пока работают агенты, чат и так отвечает моделью агентов (фаза 10), и это правильно. Но
   ручная смена модели стоит до 1.5–2 минут.
4. **Простаивающая модель не мешает Consumer'у ни в RAM, ни в VRAM.** RAM 16 GiB: 23.5–25 GB/с,
   0 промахов и с моделью, и без неё. **VRAM 6 GiB рядом с простаивающим Coder-Next (10.1 GB):
   319.8 GB/с, хотя вместе это 16 GB на 12-гигабайтной карте.** Драйвер молча вытеснил
   видеопамять простаивающей модели (фаза 2). Сторонней программе выгрузка для этого не
   нужна, но платит модель: её следующий запрос найдёт свои веса в системной памяти. Насколько
   это её замедлит — фаза 6.
5. **Модель 27B полностью на GPU, но держит ещё 11.8 GB RAM:** это отображённая (mmap) копия
   файла, которую llama.cpp прочитал для загрузки в VRAM. Страницы чистые и больше не нужны,
   Windows заберёт их первыми под давлением без потерь. Но по счётчикам они «заняты». Проверка
   под давлением — фаза 5.
6. **Commit заметно больше весов в RAM** (4B: +9.4 GB при файле 2.7 GB). Скорее всего, это
   резерв Windows (WDDM) под видеопамять и закреплённые буферы CUDA. Commit — не физическая
   память: решения принимаются по доступной RAM.
7. Скорость прохода RAM Consumer'а между запусками — 19.9–25.0 GB/с без промахов. Это разброс
   самого Consumer'а. Главный сигнал — страничные промахи, а GB/с вторичен.

**Решение по H4.** Выгрузка работает стандартными средствами: память отдаётся полностью, а
возврат из standby укладывается в 10 с для всех моделей. Контроллер не нужен (критерии
остановки №1 и №4). Делаем **У2** — политику выгрузки в NETRUNNER. Пороги по замеру:

| Модель | Цена возврата: тёплый / холодный | Политика |
|---|---|---|
| Эмбеддинги, 4B | ≤ 3.3 с / ≤ 9 с | Выгружать после простоя (например, 10 мин) — дёшево в любом случае |
| 27B | 7.8 с / 31 с | Выгружать после долгого простоя или при давлении памяти |
| Coder-Next | 8.6 с / ~100 с | Только при давлении памяти или долгом простое; не выгружать, пока работает движок агентов |

- Давление памяти уже видит RI-монитор (этап 2): доступная RAM и занятость VRAM всеми процессами
  по `nvidia-smi`.
- Возвращать модель после выгрузки можно сразу по первому запросу, без предупреждения
  пользователя, если её файлы в standby. Иначе показывать в строке статуса «загрузка с диска,
  ~N с»; N считается по размеру и скорости диска фазы 1.
- Порог H4 для приёмки У2: Consumer после выгрузки получает освобождённую память на полной
  скорости (выполнено), возврат из standby ≤ 10 с (выполнено для всех четырёх моделей).

### Фаза 4 — H3: сохранение контекста гибридного Coder-Next (2026-11-06)

Замер: `test/nsc/me-phase4.live.test.ts`, данные — `nsc\me\phase4\phase4.json`. Coder-Next с
настройками агентов (65K × 2 слота) и `--slot-save-path`. Диалог: системный промпт и ~26 тыс.

1. Состояние сохранено (HTTP 200, 7494 токена).
2. Восстановлено (7494 токена, 0.26–0.28 с).
3. Следующий запрос его использует: из кэша 7494 токена.
4. Полного prefill нет: дочитано 27 токенов вместо 7521.
5. Результат в допуске — он вообще побитно совпадает с живым сервером. Для сравнения: прочитать

токенов — около 3.4 GB. С этого SATA-диска 395 MiB читаются за ~0.7 с холодными и за 0.27 с из
standby.

**Решение по H3 (сохранение состояния): подтверждена стандартными средствами llama.cpp.** Делаем
**У3** — приостановку с сохранением слотов. Что нужно предусмотреть при реализации:
- папка слотов (например, `%USERPROFILE%\NETRUNNER\slots`) с ограничением общего размера и
  удалением файла после восстановления или по возрасту;
- сохранять только слоты с содержимым: агентский слот на 65K токенов — до 3.4 GB на диске;
- **не проверено:** выберет ли сервер восстановленный слот сам, без `id_slot`, по сходству промпта
  (`--slot-prompt-similarity`). В замере слот задавался явно. Это проверяется при реализации У3,
  на запросах OpenCode;
- восстановление сокращает только чтение промпта. Загрузка весов (8–10 с из standby, до ~100 с с
  диска, фаза 3) остаётся.

**Попутно (фаза 4).** Чтение промпта в 7.4K токенов шло со скоростью ~360 ток/с, а промпта в 4.3K в фазе 0 —
614 ток/с. Чтение длинных промптов на гибридной модели замедляется сильнее ожидаемого. Для агентов
это важно, но к памяти не относится — отдельный вопрос.

### Фаза 5 — H3 честно: другая программа реально заняла память (2026-11-06)

Замер: `test/nsc/me-phase5.live.test.ts`, данные — `nsc\me\phase5\`. Coder-Next с настройками
агентов, 3 повтора на сценарий. «Ответ» — промпт ~30 токенов и 64 токена генерации.

**Ограничение замера.** Предел commit здесь 67.9 GB: 64 GB RAM и файл подкачки 4 GB, размером
которого управляет Windows. Consumer брал не больше «предел − занято − 4 GB», чтобы не заставить
Windows расширять файл подкачки и не отказать в памяти другим программам. Поэтому Consumer не
может создать давление сверх доступной памяти, пока модель загружена. Проверить «Windows
отбирает страницы у загруженной модели» этим замером нельзя.

| Сценарий | Consumer | Возврат: загрузка / до ответа | Первый ответ / второй |
|---|---|---|---|
| Выгрузка, никто не занимал (фаза 3) | — | 7.8 с / 8.6 с | — |
| **Выгрузка → Consumer 16 GiB → возврат** | 16 GiB, 7.0–8.1 GB/с при записи | **24.1–25.6 с / 29.1–31.1 с** | 16.1–16.4 / 21.3–22.3 ток/с |
| **Выгрузка → Consumer 28 GiB → возврат** | 28 GiB | **48.6 с (3 из 3) / 53.3–53.9 с** | 16.0–17.6 / 21.2–22.1 |
| Coder-Next загружен (mmap), Consumer 28 GiB рядом | 28 GiB, проходы 23.3–24.2 GB/с | модель не выгружалась | после: 23.0–25.9, ещё раз: 21.9–22.7 |
| Qwen 27B загружен, Consumer 28 GiB рядом | 28 GiB, 19.1–22.1 GB/с | — | 15.4–15.7 до, 15.7 после |
| **Закреплённые веса** (`-lm none` + кэш 6 GB) | **0: места в commit нет** | **загрузка 102.5 с; возврат после выгрузки 100.9 с** | 27.1 / 27.7 |

**Находки.**
1. **Цена возврата растёт с тем, сколько памяти заняла другая программа:** 8.6 с, если никто,
   ~30 с после 16 GiB и ~54 с после 28 GiB. Это файлы модели, вытесненные из standby и
   прочитанные снова с SATA-диска. Разброс между повторами меньше 4 %. **Порог H3 «≥ 16 GB и
   возврат ≤ 10 с» на этом диске не выполняется** — 29–31 с. Выполняется только тёплый случай,
   когда освобождённую память никто не использовал.
2. **Первый ответ после любой загрузки на ~25 % медленнее** (16–17.6 против 21–22 ток/с), второй
   уже нормальный. Это не следствие Consumer'а: так же было в сценарии без выгрузки. Это
   прогрев после загрузки.
3. **Загруженная модель на mmap уже эластична настолько, насколько позволяет commit.** Рядом с
   простаивающим Coder-Next другая программа получила 28 GiB на полной скорости, и модель после
   этого не замедлилась. То же для 27B. Выгрузка добавляет к этому ~13 GB физической RAM, ~15 GB
   commit и 10 GB VRAM (фаза 3).
4. **Закреплённые веса несовместимы с эластичностью — подтверждено.** С `-lm none` Coder-Next
   занимает 76.3 GB commit из 77. **Windows сама расширила файл подкачки с 4 до 13.4 GB**, чтобы
   модель загрузилась. Доступно другим программам — 7.6 GB, а занять что-то в commit они уже не
   могут без нового расширения файла подкачки. Возврат после выгрузки — 101 с: веса заново
   закрепляются, и неважно, занимал ли кто-то память. После выгрузки файл подкачки вернулся к
   4 GB. Плата за это — генерация 27–28 ток/с против 21–22.
5. **Не проверено:** что Windows забирает у 27B его ненужную копию файла (11.8 GB, фаза 3) без
   потерь. Для этого нужно давление сверх доступной памяти, а значит, расширение файла подкачки.
   Без вашего согласия я этого не делаю.

**Решение по У4.**
- `-lm none` **не включать автоматически.** Сейчас `serverArgs` добавляет его всегда, когда в
  профиле есть кэш экспертов. Это бывает, если Coder-Next служит чат-моделью и пользователь нажал
  ПОДОБРАТЬ: тюнер найдёт +40 %, а цена — почти вся память системы и 100 с возврата.
- Варианты: (а) кэш экспертов без `-lm none` по умолчанию — 24.2 ток/с вместо 30.5 (этап 5); (б)
  `-lm none` только как явный режим «модель владеет памятью» с предупреждением на карточке.
- **Выбор пользователя (2026-11-06): (а), кэш без `-lm none`. Сделано:** `serverArgs` больше не
  добавляет `-lm none` к кэшу экспертов, а юнит-тест проверяет, что его нет. 205 тестов, tsc чисто.
  Тюнер по-прежнему решает замером, включать ли кэш. Теперь он меряет кэш на mmap: на чате ~+22 %
  вместо +40 %, загрузка 8–9 с, веса Windows может забрать. Режима «модель владеет памятью» нет.
- **Фаза 8 (H5) теперь оправдана по правилу плана:** конфликт «быстро или эластично» подтверждён.
  Маленький закреплённый буфер (фаза 1: 3.4 MB дают ~90 % скорости полного закрепления) может
  дать скорость `-lm none` без потери эластичности.

| `--fit-target 3072` + 3 GiB | 184–203 GB/с | 23.9 |
| **`--cpu-moe` + 3 GiB / + 6.25 GiB** | 188–213 GB/с | **22.5 / 22.5 — без потерь** |

Consumer рядом с работающей моделью получает ~200 GB/с вместо 320: две программы делят один GPU,
и это не вытеснение. При вытеснении было бы ~12 GB/с.

CPU Consumer на 8 потоков рядом с генерацией замедляется на 4–5 %, и по умолчанию, и с `--cpu-moe`
(0.575 → 0.60 с за проход). Модель при этом не замедляется. `--cpu-moe` заметно не добавляет
нагрузки на процессор для других программ: Coder-Next и по умолчанию считает большую часть
экспертов на CPU.

**Выводы.**
1. **H1 для Coder-Next подтверждена стандартными средствами:** `--cpu-moe` отдаёт 5.35 GB
   видеопамяти за −9 % генерации и −6.5 % prefill. Порог H1 — «≥ 3 GB при ≤ −10 %» — выполнен
   (с оговоркой про одну загрузку).
2. **Частичное размещение хуже полного.** `--fit-target` при сильном урезании выносит на CPU и
   обычные (не экспертные) веса — отсюда −51 % на 4.2 GB против −9 % у `--cpu-moe` на 4.8 GB.
   `--n-cpu-moe N` при `--fit` не экономит видеопамять (42) или переполняет её (36). Кэш экспертов
   на mmap для экономии видеопамяти проигрывает `--cpu-moe` и по объёму, и по скорости.
3. **Переполнение видеопамяти вдвое замедляет модель**, и никто не получает ошибки. С `--cpu-moe`
   у модели запас ~6 GB: соседняя программа может взять 3–6 GB без вреда для обеих.
4. **У плотной 27B эластичности видеопамяти нет:** 2 GB стоят −53 %, 4 GB — −73 %.
5. Контекст 32K вместо 65K не меняет видеопамять Coder-Next: KV-кэш у гибридной модели мал.
6. **Поправка к фазе 3:** после настоящей работы Coder-Next держит ~41–44 GB RAM (страницы
   экспертов в рабочем наборе), а не 13 GB. В фазе 3 память мерилась после запроса в 1 токен,
   когда большая часть экспертов ещё не была прочитана. Сценарий фазы 5 «Consumer 28 GiB рядом с
   загруженной моделью» тоже был после коротких ответов. При полностью прогретой модели другим
   программам доступно меньше: около 20 GB вместо 30.

**Решения.**
- **У1 «ЭКОНОМИЯ VRAM»:** переключатель на карточке MoE-модели, как БЫСТРЫЙ РЕЖИМ, → `--cpu-moe`
  без кэша. Подсказка: «−5 GB видеопамяти, ~−9 % скорости». Только для MoE — плотным моделям не
  предлагается. Не включать по умолчанию: −9 % заметны, а выигрыш нужен, только когда видеопамять
  нужна чему-то ещё. Автоматический откат тюнера (≥ 15 % замедления на 5 прогонах) поймает
  устойчивые выбросы вроде 18.4.
- **У5 «Запас видеопамяти»:** поднимать запас для всех моделей (`--fit-target`) дорого — 27B
  теряет половину. `--fit` и так учитывает видеопамять, занятую другими программами, в момент
  загрузки. Опасен момент, когда другая программа занимает видеопамять *после* загрузки модели.
  Поэтому У5 — наблюдение и реакция: RI-монитор по `nvidia-smi` видит, что видеопамяти почти не
  осталось (чужая занятость растёт, свободно < ~0.5 GB), и показывает «видеопамять переполнена —
  модель может работать вдвое медленнее». Для MoE-модели — кнопка «ЭКОНОМИЯ VRAM» (перезагрузка
  4–8 с), для плотной — «выгрузить». Автоматически ничего не перезагружается.

## Реализация У1–У5 (2026-11-06)

| | Что сделано | Где |
|---|---|---|
| **У1** | Переключатель **ЭКОНОМИЯ VRAM** на карточке MoE-модели (под БЫСТРЫМ РЕЖИМОМ) → `--cpu-moe` без кэша экспертов. Заменяет кэш из профиля тюнера. Вступает в силу при следующей загрузке | `settings.vramSaver`, `LaunchProfile.cpuMoe`, `operatorProfile()` и `serverArgs` в `llamacpp.ts`, `VramSaver` в `ModelVault.tsx` |
| **У2** | Раз в минуту `idleSweep()` выгружает модели, которыми не пользовались: малые (≤ 6 GiB) — через 10 мин по умолчанию, большие — никогда по умолчанию (выбор 5/10/30/60/120 мин). Когда доступной RAM < 1 GiB, выгружается любая модель, простаивающая ≥ 2 мин. Модель движка агентов не выгружается. Использование считается и по запросам через NETRUNNER, и по счётчикам токенов сервера (OpenCode ходит к серверу напрямую). Панель **ПРОСТАИВАЮЩИЕ МОДЕЛИ** в MODEL VAULT; на карточке загружающейся большой модели — «с диска до ~N с» | `idleSweep`, `shouldUnloadIdle` в `llamacpp.ts`, таймер в `index.ts`, `settings.idleUnload`, `IdleUnloadPanel` |
| **У3** | Чат-сервер запускается с `--slot-save-path` (`%USERPROFILE%\NETRUNNER\slots`). Перед выгрузкой по простою сохраняются слоты с контекстом ≥ 1024 токенов. При следующей загрузке той же модели с той же формой (контекст × слоты) они восстанавливаются, файлы удаляются. Хранятся не дольше суток и не больше 16 GB | `suspendSlots`, `restoreSlots`, `pruneSlotFiles` |
| **У4** | `-lm none` не используется (фаза 5, решение пользователя) | `serverArgs` |
| **У5** | Находка RI-монитора «VRAM занята другими» теперь говорит об измеренном последствии (Coder-Next вдвое медленнее) и даёт действие прямо в SYSTEM MONITOR: для MoE-модели — **ЭКОНОМИЯ VRAM** (включает режим и выгружает модель, следующий запрос загрузит её с ним), для плотной — **ВЫГРУЗИТЬ**.
