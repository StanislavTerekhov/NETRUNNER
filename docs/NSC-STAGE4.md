# NSC, этап 4 — эксперты в VRAM

Дата: 2026-11-04. Данные — `%USERPROFILE%\NETRUNNER\nsc\stage4\`.

## Что возможно в llama.cpp b12020

- **Статически поместить отдельных «горячих» экспертов в VRAM нельзя.** Эксперты слоя хранятся одним тензором (`blk.N.ffn_*_exps`, все 512 экспертов сразу), а `-ot` переносит только тензор целиком. Для этого нужен свой форк с разрезанными тензорами (этап 5).
- **Переносить целые слои экспертов** (так уже делает `--fit`) для генерации всё равно, какие слои выбрать. Каждый токен использует 10 экспертов в каждом слое, поэтому любой слой на GPU экономит одинаково на гигабайт VRAM.
- **В b12020 нашёлся встроенный GPU-кэш экспертов: `--moe-cache-mib N`.** Эксперты лежат в RAM, а видеокарта держит кэш недавно использованных. Все эксперты считаются на GPU, недостающие подкачиваются по PCIe. По сути это динамический кэш из этапа 5 — без форка и без компилятора.

## Замер

`test/nsc/stage4-moe-cache.live.test.ts`: Coder-Next как у агентов (64K × 2 слота, 8 потоков). Задачи как в базовой линии, по два прохода; в таблице второй, с заполненным кэшем.

| Конфигурация | Генерация | Русский / код / после длинного контекста | Длинный промпт | CPU NETRUNNER | VRAM |
|---|---|---|---|---|---|
| Как сейчас (2 замера) | 21.4 / 21.7 | 21 / 21 / 22–23 | 611–625 | 21 % | 10.9–11.1 GB |
| + кэш 1 GB | 12.7 (−41 %) | 18 / 10 / 10 | 602 | 23 % | 11.1 |
| + кэш 2 GB | 20.0 (−7 %) | 26 / 18 / 16 | 600 | 21 % | 11.1 |
| + кэш 4 GB | 22.9 (+6 %) | 29 / 22 / 18 | 593 | 20 % | 11.3 |
| Все эксперты в RAM + кэш 4 GB | 22.5 (+4 %) | 29 / 21 / 18 | 589 | 3 % | 9.8 |
| **Все эксперты в RAM + кэш 6 GB** | **26.4 (+22 %)** | **34 / 25 / 21** | 583 | **3 %** | 11.75 |

- Выигрыш сильно зависит от задачи: на русском тексте +63 %, на коде +16 %, на ответе после длинного контекста −9 %. Это совпадает с анализом экспертов на этапе 0: набор горячих экспертов зависит от домена.
- Процессор почти свободен (3 % вместо 21 %). Цена — PCIe: 8–11 GB/с подкачки вместо ~1.5 GB/с.
- Маленький кэш вредит: 1 GB даёт −41 %, потому что промахи по PCIe стоят дороже, чем работа на CPU.

## Проверка на реальной работе агентов

Тот же агентный конвейер, что на этапе 1, с кэшем 6 GB (`NETRUNNER_SERVER_EXTRA_ARGS`, только для замеров):

| Шаг | Без кэша (этап 1) | С кэшем 6 GB |
|---|---|---|
| ARCHITECT | 23.3 ток/с | 20.9 |
| CODER | 22.4 | 18.5 |
| DEBUGGER | 23.5 | 18.7 |
| REVIEWER | 22.5 | 19.6 |

**У агентов кэш хуже на 10–17 %.** Шаги агентов генерируют код после 7+ тыс. токенов контекста с инструментами. Там задействовано больше разных экспертов, и кэш промахивается. Smoke при этом 60/60: качество не пострадало, только скорость.

## Автотюнер теперь пробует кэш, и меряет то, для чего модель используется

- Кэш стал настройкой автотюнера (`moeCacheMib`): для MoE-моделей пробуются треть и половина VRAM (4 и 6 GB на 12 GB). Маленькие кэши не пробуются, потому что по замеру они вредят.
- Первая версия тестировала все модели одним набором: короткий код, русский текст, длинный промпт почти без генерации. Она выбрала кэш 6 GB для Coder-Next (+19 % на тесте), а реальный конвейер агентов оказался медленнее. **Тест не соответствовал работе.**
- Исправлено: модель агентов подбирается на агентном тесте (`use: 'agent'`) — генерация кода после короткого и после ~7 тыс. токенов кода. Модели чата подбираются на прежнем тесте.
- Повторный подбор Coder-Next: кэш 6 GB даёт 19.0 против 20.9 ток/с (−9 %), кэш 4 GB — 17.7 (−15 %). Оба отклонены. **Решение тюнера теперь совпадает с реальным конвейером.**

## Итог

| | Результат |
|---|---|
| Горячие эксперты статически через `-ot` | невозможно в обычной llama.cpp (тензор на слой) |
| Встроенный кэш экспертов, чат | +22 % генерации (русский +63 %), CPU свободен |
| Встроенный кэш экспертов, агенты | −10…−17 % — для модели агентов не включается |
| Автотюнер | пробует кэш сам; для модели агентов меряет агентную работу |

На этой машине Coder-Next служит моделью агентов, поэтому кэш ей не включается. Кэш выиграет, если MoE-модель используется как модель чата: тюнер найдёт это сам.

## Этап 5

Встроенный кэш уже даёт динамическое кэширование. Свой форк имел бы смысл ради более умной политики кэша: заранее закреплённый набор по домену (этап 0) плюс LRU для остальных экспертов. Это может убрать проигрыш на длинных контекстах. Для форка нужны VS Build Tools и CUDA Toolkit, их на машине нет. Ставить что-то можно только с вашего согласия.
