# Фаза 4 — MULTI-AGENT SYSTEM: отчёт

Дата: 2026-10-30. Статус: **завершена**. Версия 0.4.0.

## Что сделано

| Требование спецификации | Реализация |
|---|---|
| Роли Architect / Coder / Debugger / Reviewer / Operator | Агенты OpenCode с собственными промптами и правами (Фаза 3); ARCHITECT, REVIEWER и OPERATOR не могут редактировать файлы, ARCHITECT не запускает команды |
| Очередь задач | `TaskQueue` в main-процессе, таблица `tasks` в SQLite. Строго последовательно: одна задача — одна сессия OpenCode; перед каждой — git-чекпоинт |
| Мультиагентный конвейер | Кнопка PIPELINE ставит в очередь ARCHITECT → CODER → DEBUGGER → REVIEWER для одной цели; каждый шаг получает итоговые ответы предыдущих шагов (общий контекст проекта) |
| Восстановление после ошибок | Упавший шаг отменяет оставшиеся шаги своего конвейера («previous step (coder) failed») — без каскада правок на сломанной базе. RETRY ставит задачу заново; задачи, бывшие в работе при закрытии приложения, помечаются `interrupted` |
| Отмена | CANCEL для ожидающих задач, ABORT для выполняющейся (`session.abort`) |
| Сохранение сессий | SQLite `userData/netrunner.db` (WAL): история чатов Neural Core (JSON-файлы Фазы 2 импортируются один раз, папка сохраняется как резервная копия), очередь и результаты задач, индекс памяти. Сессии самих агентов хранит OpenCode в изолированном каталоге |
| Локальная память и семантический поиск | Экран MEMORY: индексация воркспейса (фрагменты по 60 строк с перекрытием 10), эмбеддинги **`qwen3-embedding:0.6b`** через Ollama (1024 измерения), хранение в **sqlite-vec** (`vec0`, partition key = воркспейс, косинусная метрика). Повторная индексация пересчитывает только изменённые файлы и удаляет исчезнувшие. Результат поиска открывает файл на нужной строке |
| Использование памяти | Переключатель MEMORY в AGENT CONTROL (найденный код добавляется к каждой задаче/шагу) и в NEURAL CORE (к сообщению) |

Технический выбор: вместо нативного `better-sqlite3` используется встроенный в Electron 42 модуль **`node:sqlite`**
(Node 24.19, SQLite 3.53.3) — не нужна пересборка под ABI Electron и Visual Studio Build Tools. sqlite-vec — готовая
`vec0.dll` из npm, распаковывается из asar при сборке.

## Найденные и исправленные дефекты

1. Unsloth во время обучения FORGE записал кэш скомпилированного кода (`unsloth_compiled_cache`, 2,6 МБ) в папку `forge/`
   репозитория — он раздувал индекс памяти. Удалён; `train_qlora.py` теперь работает из каталога FORGE; папка добавлена в
   `.gitignore` и в исключения индексатора.
2. `vec0.dll` не загружается SQLite из asar-архива — добавлено в `asarUnpack`.

## Ограничения

- Конвейер строго последовательный, как требует спецификация; параллельного выполнения нет (нужна изоляция файлов
  через отдельные worktree и разрешение конфликтов — не реализовано).
- Ответы агентов в транскрипте показываются как текст: Markdown (заголовки, таблицы) не рендерится.
- Модель эмбеддингов 0.6B выбрана ради скорости; `qwen3-embedding:4b`/`8b` точнее, но медленнее (не измерялось).
  Смена модели переиндексирует воркспейс автоматически.
- ripgrep по-прежнему не поставляется (блокер из Фазы 3, вы решили отложить): инструменты `grep`/`glob` агента падают,
  агенты обходятся `read`/`bash`.
